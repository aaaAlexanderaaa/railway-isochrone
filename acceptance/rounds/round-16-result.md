# 验收报告（round-16 结果）

- 验收人角色：出差销售，兰州出发，今晚 21:30 前后、单程 2–3 小时、最好直达；明天 21:30 前必须到青岛。
- 产品：http://127.0.0.1:8787
- 结论：**不可用**（去程圈可用，硬约束「明天 21:30 前到青岛」未被接住）。

## 1–2. 核对

去程查询是对的：出发地兰州、今晚 17–24、≤3h、仅直达口径下能给出定西/西宁等合理候选。

验收者没有把「青岛」填进第④步（当时摘要仍写「对端 B / 往返圈」，查询旁只有「还要赶回出发地」）。报告把产品理解成：不能指定后续目的地、有 10 小时上限、没有到达截止。这些都与界面事实不符——产品可以做「兰州出发圈 ∩ 明天 21:30 前能赶到青岛」，交集为空时也应是诚实答案。上下文无关用户完不成「明天必须到青岛」= 入口不够显眼，且空结果文案仍用「B 端」行话。

## 3. 处置

| # | 问题 | 处置 |
|---|---|---|
| 1 | 「明天 21:30 前到青岛」藏在「对端 B」里，用户当功能不存在 | **修**：④ 改名为「还要赶到某地 / 赶回出发地」；placeholder「必须赶到的城市，如青岛」；查询旁增加「还要赶到某地」（打开④、勾选只看还能赶到、焦点落到城市框） |
| 2 | 「最晚到达」被理解成必须赶到青岛的时刻 | **修**：改成「去程最晚到站」，并写明后天赶到青岛请填④ |
| 3 | 空交集被说成查询失败 / 「B 端条件」 | **修**：状态栏与列表空态用「从 A 出发、预算内没有城市还能赶到 X」；并附上 A→X 本身是否可达的提示 |
| 4 | 选定必须赶到的城市后仍显示全部出发圈 | **修**：选定城市后默认勾选「只看还能赶到该城市」 |
| 5 | 去程数据（兰州今晚 2–3h） | 未发现错误 |

## 4. 可用性

**不可用**（硬约束「明天 21:30 前到青岛」没有被产品接住）。修复后 round-17。
